# Scalability Design: u2-contract-api

| Area | Design | Serves |
|---|---|---|
| Statelessness | No session, no in-memory data between requests, no local files. Any request can go to any instance. | NFR5.8 |
| Scaling approach | One instance, vertical scaling only. A second instance behind a load balancer needs no code change, only the same database and configuration. | NFR5.8 |
| Concurrency | Each create request has its own database context and transaction. Ids are generated by the application (UUIDs), so concurrent saves never wait on a shared counter. Nothing in the create path uses a lock or a unique name check (BR1.3). | NFR5.7 |
| Data growth | Child rows hold the contract id in an indexed column. No partitioning: 10,000 contracts times 10,000 rows is within what one PostgreSQL table handles. | NFR5.6, NFR5.9 |
| Indexes | `contracts(start_date desc, name, id)` for the list order; `payment_streams(contract_id)`, `payment_schedule_entries(contract_id, due_date)`, `expense_schedule_entries(contract_id, period_start)`. | NFR5.9 |
| Capacity thresholds | None defined. If the list passes 100,000 contracts, change to keyset paging; this is a recorded future decision, not part of this version. | NFR5.6 |
